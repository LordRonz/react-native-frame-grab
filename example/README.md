# frame-grab bench

Device harness for `react-native-frame-grab`. Two things live here:

- **Acceptance matrix** — the correctness checks that a JavaScript mock cannot
  make: real decoding, orientation, atomic replacement, destination reservations,
  queue overflow. (`src/harness.ts`)
- **Benchmark** — the workloads, metrics and competitor adapters from
  `IMPLEMENTATION_PLAN.md` section 17. (`src/benchmark.ts`, `src/competitors.ts`)

## Setup

```bash
cd example
npm install --legacy-peer-deps
npx expo prebuild --clean          # generates ios/ and android/
npx expo run:ios --configuration Release
npx expo run:android --variant release
```

`--legacy-peer-deps` is needed because `react-native-nitro-thumbnail@0.1.4`
pins `react-native-nitro-modules@^0.35.9` while this library targets `0.37.1`.
See the note under "What is benchmarked".

A side effect of that flag: npm nests some of Expo's own dependencies instead of
hoisting them, and Babel resolves presets relative to `babel.config.js`. So
`babel-preset-expo` is declared here explicitly. Without it Metro fails with a
confusing `Cannot read properties of undefined (reading 'transformFile')`, whose
real cause is a `Cannot find module 'babel-preset-expo'` further up the trace.

### Paths containing spaces

`expo-constants` builds its `Generate app.config` phase as
`bash -l -c "$PODS_TARGET_SRCROOT/.../get-app-config-ios.sh"`. `bash -c`
re-parses its argument as a command line, so an unquoted path splits on spaces
and the build dies with `No such file or directory: /Volumes/T7` (or whatever
precedes your first space).

There are **two** such phases, fixed in two different places because they are
generated by two different things:

| Phase | Problem | Fix |
| --- | --- | --- |
| `expo-constants` » Generate app.config | `bash -l -c "$PODS_TARGET_SRCROOT/..."` — `bash -c` re-parses its argument | `patches/expo++expo-constants+57.0.18.patch`, reapplied by the `postinstall` hook |
| app target » Bundle React Native code and images | a backtick substitution whose *result* is executed unquoted | `plugins/withSafeBundleScriptPaths.js`, reapplied on every `expo prebuild` |

The bundle phase lives in the generated `ios/` project rather than in
`node_modules`, so patch-package cannot reach it — hence the config plugin. If
you bump the Expo SDK, regenerate the patch and re-check the plugin still
matches (it warns loudly if it finds nothing to rewrite):

```bash
npx patch-package expo/expo-constants
```

Two instances is the honest signal here: nothing prevents a third. **Moving the
checkout to a path without spaces fixes the whole class**, and lets you delete
both workarounds.

To check the JS graph without building native:

```bash
npx expo export --platform ios
npx expo export --platform android
```

Release builds on a physical device. Debug builds and simulators do not measure
the same thing, and the app says so in its own output.

## What is benchmarked

| id | library | frame selection exposed | notes |
| --- | --- | --- | --- |
| `frame-grab` | this library | yes (`fast` / `precise`) | subject under test |
| `expo-video+image-manipulator` | `expo-video` + `expo-image-manipulator` | no | **the baseline** — the pipeline being replaced. All `% vs` figures are against this row |
| `expo-video-thumbnails` | `expo-video-thumbnails` | no | no width bound in its API, so the downscale + re-encode is adapter overhead |
| `nitro-thumbnail` | `react-native-nitro-thumbnail` | yes (`onlySyncedFrames` / `timeToleranceMs`) | closest comparable: also Nitro, also thumbnail-specific |
| `nitro-video` | `@mindinventory/react-native-nitro-video` | — | skipped, not installed |

Workloads that need `precise` are reported as skipped for the rows that do not
expose a selection mode, rather than silently compared against default
extraction.

**`nitro-thumbnail` version caveat.** It declares
`react-native-nitro-modules@^0.35.9`; this library needs `0.37.1`, and on a `0.x`
range those do not overlap. The JS resolves under `--legacy-peer-deps`, but its
committed `nitrogen/generated` output was produced by nitrogen 0.35 and gets
compiled against 0.37 headers. **If the native build breaks, that is the reason** —
set `available: false` with that as the `unavailableReason` in
`src/competitors.ts` and move on. A benchmark row that cannot be built honestly
is a skipped row, not a win.

Three things are normalised in its adapter so the comparison is fair, all
commented at the call site: its `maxHeight` default of 512 is raised so width is
the only binding constraint, `cacheName` is left unset so the benchmark is not
timing cache hits, and the move out of its private cache directory into
`destinationUri` is counted as adapter overhead.

## Fixtures

The benchmark runs against whatever video you select. Two sources are offered:

1. **Media library** — granted on first launch. This is the real-world path:
   `content://` on Android, a Photos-backed local file on iOS.
2. **Pushed fixtures** — anything in the app's `Documents/fixtures/` directory.

For the acceptance matrix you want the fixture set from plan section 16:

| Fixture | Why |
| --- | --- |
| H.264 landscape and portrait | Baseline |
| Asymmetric TOP/LEFT markers at 0/90/180/270 rotation, plus square frames | Orientation. Dimensions alone cannot resolve 180 or square, so these must be looked at |
| 4K H.264 and HEVC | Memory and codec support |
| Long-GOP, variable frame rate, very short | Frame selection |
| Source narrower than `maxWidth` | No-upscale rule |
| Extreme aspect ratio | Output area limit |
| Corrupt/truncated, audio-only | Failure paths (a corrupt file is also generated at runtime) |
| Visible frame numbers or timecode | Verifying which frame was actually selected |

Pushing them:

```bash
# Android
adb push fixtures/. /sdcard/Android/data/com.margelo.framegrab.bench/files/fixtures/

# iOS: Xcode > Window > Devices and Simulators > select app > Download/Replace Container,
# or drop the files into the app's Documents/fixtures folder over Files.app.
```

## What the numbers mean

Reported per implementation and workload: p50/p95 latency, sample count, error
rate and codes, first-after-launch latency (kept out of the percentiles), output
dimensions and byte size, and JS-thread FPS during the run. For this library
only, native phase timings are broken out: queue wait, source setup, metadata,
extraction, encode+write, finalize.

The whole suite runs three times, at native scheduler bounds of 1, 2 and 4
concurrent jobs, which is what picks the published default.

Not measured here, on purpose:

- **Peak process/native memory, file descriptors, thermal state.** Not readable
  from JavaScript. Attach Instruments (Allocations + VM Tracker) or Android
  Studio's Profiler to the same run.
- **Visual quality.** Equal numeric JPEG quality is not equal visual quality
  across encoders. Compare the written files.
- **Cold caches.** "First after launch" is reported separately, but nothing here
  proves the OS page cache was cold.

Each run writes `report-<concurrency>x-<timestamp>.json` into the app's cache
directory alongside the generated thumbnails.

## Adding a competitor

`src/competitors.ts` holds one adapter per implementation. An adapter must write
the JPEG to `destinationUri` — if a library returns an ArrayBuffer or a cache
URI, the cost of getting it to disk belongs in the measurement, and any adapter
overhead belongs in the `selection` / `label` fields so the comparison stays
honest.

Metro resolves `require` at build time, so an optional dependency cannot be
probed at runtime. `@mindinventory/react-native-nitro-video` is listed as
unavailable with a stated reason; install it and fill in the adapter to include
it.
